# 验证码 Lua 并发测试与 RedisPool 性能分析

## 1. 分析范围

本报告分析以下测试：

1. Lua 验证码原子消费正确性测试。
2. `RedisPool size=10` 与 `size=32` 的五轮对比测试。
3. 关闭调试日志前后的性能变化。
4. `RedisPool size=10` 下的 `1000 请求 / 1000 并发` 冲击测试。
5. `error=1009` 的含义边界。
6. RedisPool 是否需要扩容。
7. 后续改为无锁队列时的验证标准。

本报告中的延迟均为客户端观察到的端到端延迟，包含客户端线程调度、TCP 建连、HTTP 处理、GateServer 排队、RedisPool 借还连接、Redis Lua、响应发送等全部开销，并不等同于 Redis 命令本身耗时。

---

## 2. Lua 原子消费正确性结论

所有已完成测试均表现为：

```text
同一验证码最多只有 1 个请求进入后续注册流程
其余请求均返回 error=1003
Redis key 最终不存在
未出现网络或超时错误
```

典型结果：

```text
error=0    ：1
error=1003 ：999
```

部分轮次为：

```text
error=1009 ：1
error=1003 ：999
```

这同样表示 Lua 原子消费正确。唯一一个请求已经成功消费验证码，但在后续注册流程中返回 `1009`。`1009` 不代表验证码被重复消费。

原子性失败的真正判定条件是：

```text
同一轮中，进入后续注册流程的请求数量超过 1 个
```

截至本报告记录的测试，没有发生该问题。

## 3. RedisPool size=10 与 size=32：五轮对比

### 3.1 中位数对比

| 指标 | size=10 | size=32 | size=32 相对变化 |
|---|---:|---:|---:|
| 总耗时 | 2.312 s | 2.534 s | +9.6% |
| 平均请求延迟 | 984.05 ms | 1103.68 ms | +12.2% |
| P50 | 234.68 ms | 304.65 ms | +29.8% |
| P90 | 2181.59 ms | 2428.11 ms | +11.3% |
| P95 | 2201.89 ms | 2449.95 ms | +11.3% |
| P99 | 2219.54 ms | 2470.42 ms | +11.3% |
| 中位吞吐量 | 432.53 req/s | 394.63 req/s | -8.8% |

### 3.2 平均值对比

| 指标 | size=10 平均 | size=32 平均 |
|---|---:|---:|
| 总耗时 | 2.130 s | 2.425 s |
| 请求平均延迟 | 921.25 ms | 1063.87 ms |
| P50 | 259.01 ms | 293.20 ms |
| P95 | 2041.30 ms | 2312.58 ms |
| P99 | 2058.25 ms | 2351.67 ms |

### 3.3 结论

五轮中位数和平均值都表明：

```text
size=32 没有稳定提升吞吐量
size=32 的 P50、P95、P99 整体更高
size=10 已能满足当前 Redis 访问并发
```

因此当前推荐：

```ini
[RedisServer]
size = 10
```

现有数据不支持把 RedisPool 固定提升到 32，也不支持继续盲目扩大到 50、100 或更多。

## 4. 去除调试日志的影响

在 `size=32` 条件下，对比有调试日志和去除调试日志：

| 指标 | 有调试日志 | 去除调试日志 | 改善 |
|---|---:|---:|---:|
| 总耗时 | 2.302 s | 1.934 s | 16.0% |
| 平均延迟 | 1000.96 ms | 801.52 ms | 19.9% |
| P50 | 902.29 ms | 346.14 ms | 61.6% |
| P95 | 2192.42 ms | 1708.24 ms | 22.1% |
| P99 | 2257.13 ms | 1755.10 ms | 22.2% |

结论：

```text
同步调试日志对性能有明显影响
P50 改善最明显
关闭日志后尾延迟仍然较高
```

所以日志是重要开销，但不是唯一瓶颈。压测时应关闭高频同步控制台输出；正式环境应使用异步日志或采样日志。

## 5. size=10：1000 请求 / 1000 并发冲击测试

### 5.1 两轮结果

| 指标 | 第 1 轮 | 第 2 轮 |
|---|---:|---:|
| 总耗时 | 3.054 s | 1.507 s |
| 估算吞吐量 | 327.44 req/s | 663.57 req/s |
| 平均延迟 | 2544.27 ms | 1171.83 ms |
| P50 | 2700.12 ms | 1205.95 ms |
| P90 | 2927.51 ms | 1394.61 ms |
| P95 | 2956.44 ms | 1422.38 ms |
| P99 | 2977.32 ms | 1453.93 ms |
| 最大延迟 | 2998.97 ms | 1459.16 ms |

两轮正确性均为：

```text
error=0    ：1
error=1003 ：999
网络错误    ：0
Redis key  ：不存在
```

### 5.2 波动解释

相同参数下，两轮性能差异较大。`1000/1000` 测试会同时受到以下因素影响：

```text
Python 创建和调度 1000 个线程
Windows socket、临时端口和线程调度
GateServer listen backlog
HTTP 会话创建和销毁
服务端业务线程池排队
RedisPool 借还连接
本机 CPU 和后台任务
```

因此，`1000/1000` 更适合验证瞬时冲击下的正确性与稳定性，不适合单独用于判断 RedisPool 最佳大小。

用于稳定性能比较时，应优先保留：

```text
1000 请求 / 100 并发
1000 请求 / 200 并发
```

同时把 `1000/1000` 作为冲击测试。

## 6. RedisPool 当前是否需要扩容

当前结论：

```text
不需要扩容
size=10 暂时足够
size=32 未显示稳定收益
```

原因：

1. Lua 脚本很短，单次 Redis 占用连接时间很短。
2. 请求总数不等于实际同时占用 Redis 连接的数量。
3. 真正同时执行 Redis 操作的数量受 GateServer 工作线程数限制。
4. 五轮对比没有显示 size=32 的吞吐和尾延迟改善。
5. 延迟波动更像 HTTP、线程调度、业务线程池排队或连接池实现细节造成。

## 7. 后续无锁队列优化建议

可以把 RedisPool 的内部空闲连接容器改为无锁队列，但必须先理解：

```text
无锁队列只能减少队列 push/pop 的锁竞争
不能解决连接池为空时的等待
不能消除 Redis 网络耗时
不能解决线程池任务排队
不能解决锁内 PING 或锁内重连
```

比替换容器更优先的事项：

1. 不要持连接池全局锁执行 `PING`。
2. 不要持锁执行重连和认证。
3. 正常归还连接时直接放回。
4. Redis 命令失败时才标记连接异常。
5. `BorrowConnect()` 增加超时。
6. 增加连接等待、连接重建和池使用率指标。

### 7.1 必须增加的指标

```text
borrow_count
borrow_wait_avg
borrow_wait_p50
borrow_wait_p95
borrow_wait_p99
borrow_wait_max
borrow_timeout_count
available_connections_min
connection_rebuild_count
```

### 7.2 无锁优化验收标准

优化前后保持：

```text
相同机器
相同 GateServer 工作线程数
相同 RedisPool size
关闭调试日志
相同请求数量与并发
每组预热 1 轮
每组正式运行至少 5 轮
```

同时满足：

```text
Lua 正确性不变
error=0 或 error=1009 的总数最多为 1
error=1003 为 N-1
网络错误为 0
连接无重复归还
连接无丢失
关闭服务器时无竞态崩溃
```

性能方面只有出现以下稳定变化，才能认为无锁队列有效：

```text
吞吐量中位数提升至少 10%
P95 和 P99 中位数同时下降
Borrow 等待时间明显下降
CPU 没有因忙等明显升高
```

若 Borrow P95 本来就小于 1 ms，无锁队列通常不会显著改善端到端延迟。

---

## 8. 当前瓶颈优先级判断

根据现有数据，建议排查顺序：

1. GateServer 业务线程池的任务排队时间。
2. RedisPool 是否在锁内执行 `PING`、重连或其他网络操作。
3. HTTP 会话处理、监听 backlog 和连接建立排队。
4. 同步日志输出。
5. Windows 客户端 1000 线程与 socket 调度。
6. RedisPool 容量本身。

当前没有证据表明 Redis 服务端 Lua 执行速度是主要瓶颈。

---

## 9. 最终结论

```text
Lua 原子消费：通过
1000 请求正确性：通过
1000/1000 瞬时冲击：通过
RedisPool size=10：当前足够
RedisPool size=32：无稳定收益
调试日志：存在明显性能损耗
无锁队列：可作为后续优化，但应先增加等待指标并消除锁内网络操作
```
