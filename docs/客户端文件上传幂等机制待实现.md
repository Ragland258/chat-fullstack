## 3. 已确定的架构约束

这些是已经讨论并确定的边界，后续实现不得随意破坏。

- [x] 客户端通过 ChatServer 申请预签名 URL，然后直接用 HTTP PUT 上传到 MinIO。
- [x] 文件内容不经过 ChatServer 和 FileServer 转发，避免业务服务占用大量带宽和内存。
- [x] ChatServer 负责认证用户、业务权限、Redis 上传会话和 MySQL 业务数据。
- [x] FileServer 只负责 MinIO：生成对象键、生成预签名 URL、查询对象、生成下载 URL。
- [x] FileServer 不读取 Redis，也不更新 `users` 等业务表。
- [x] `uploader_id` 只能来自已经认证的 `Connection`，不能相信客户端 JSON 中的用户 ID。
- [x] `object_key` 只能由服务端生成，原始文件名不能直接拼进对象键。
- [x] MySQL 只保存稳定的 `file_id/object_key`，绝不保存会过期的预签名 URL。
- [x] `completeUpload` 不相信客户端重新提交的大小和 MIME 类型；它必须比较 Redis 预期值和 MinIO 实际值。
- [x] Redis 保存上传过程的临时状态，MySQL 保存最终业务引用。
- [x] `RedisFileMgr` 设计为通用文件上传组件，后续复用于头像、背景、聊天图片、视频、音频和附件。
- [x] 第一版允许 `session_id == file_id == object_key`，但三者概念上仍然独立，业务代码不能依赖它们永远相等。
- [x] 用户公开资料使用统一的 `profile_version`；头像、背景、昵称或签名真正变化时递增，相同值的幂等重试不得递增。
- [x] 第一版不向好友或其他客户端主动广播资料水位；客户端优先使用本地缓存，在点击资料、进入聊天或刷新好友列表时按需拉取。
- [x] 中间件重构共享的是连接池、RAII、客户端封装等实现代码；GateServer、ChatServer 等独立进程仍分别拥有自己的连接池实例。
- [x] 公共 MySQL/Redis 基础设施不得依赖任一服务的 `ConfigMgr`、业务 `const.h`、JSON、Protobuf 或 Handler；服务读取配置后通过 `Options` 注入。
- [x] MySQL/Redis 的业务 SQL、Key 和 Lua 归对应 Repository/DAO 管理，不塞入公共连接池或通用客户端。
- [x] 不为了消除重复代码额外创建集中式 `DataServer`；当前采用共享静态库和服务内 Repository。

### 3.1 标识符职责

| 标识符 | 生成方 | 生命周期和用途 |
|---|---|---|
| `request_id` | 客户端 | 标识一次网络请求，用于日志追踪和请求/响应匹配；重试时可以改变 |
| `client_file_id` | 客户端 | 标识一次逻辑文件上传；同一任务的 `initUpload` 重试必须保持不变 |
| `session_id` | ChatServer | 标识一次服务端上传会话，供 `completeUpload` 使用 |
| `file_id` | FileServer | 文件服务暴露的稳定文件标识；第一版等于对象键 |
| `object_key` | FileServer | MinIO bucket 内的完整对象键，例如 `avatar/3/<uuid>.png` |

`completeUpload` 必须使用 `initUpload` 返回的 `session_id`，客户端不应自行推导它的格式。

## 7. M3：上传幂等与一致性加固（P1）

### 7.1 客户端约定

- [ ] `client_file_id` 从可选字段升级为非空必填字段。
- [ ] 只接受合法 UUID，或至少限制为不超过 128 字节的安全字符集合。
- [ ] 同一个文件、同一次逻辑上传的网络重试必须复用原 `client_file_id`。
- [ ] 用户重新选择文件或主动开始新任务时必须生成新的 `client_file_id`。
- [ ] `client_file_id` 不能用作 MinIO 对象键，也不能从中推导用户 ID。

### 7.2 Redis 幂等结构

当前 Session Key 继续使用：

```text
upload:session:{session_id}
```

新增幂等索引：

```text
upload:idempotency:{uploader_id}:{purpose}:{client_file_id}
    -> creating:<reservation_token>
    或 session_id
```

- [ ] 索引必须包含可信的 `uploader_id` 和 `purpose`。
- [ ] 聊天文件匹配时还必须比较 `conversation_id`。
- [ ] 相同 `client_file_id` 的 `size_bytes`、`content_type`、`purpose` 或会话不同，返回 `IdempotencyConflict`，不能覆盖原任务。
- [ ] 当前单机 Redis 先保持现有 Key；迁移 Redis Cluster 时，同一段 Lua 操作的 Key 必须使用相同 Hash Tag。

### T-11：原子预约和绑定

- [ ] 在 `RedisFileMgr` 增加 `ReserveUpload` 业务接口。
- [ ] 使用 Lua 原子区分：首次取得创建权、正在创建、已绑定 Session、元数据冲突、Redis 错误。
- [ ] 预约值使用不可猜测的 `reservation_token`，不能只用可重复的 `request_id`。
- [ ] 预约设置短 TTL，防止 ChatServer 在 FileServer RPC 中崩溃后形成永久锁。
- [ ] 只有持有相同令牌的请求可以释放预约。
- [ ] 使用 Lua 原子创建 UploadSession 并把预约绑定为 `session_id`。
- [ ] `SetAvatarHandler::InitUpload` 必须先预约，取得创建权后才能调用 FileServer。
- [ ] Redis 故障时不得继续调用 FileServer 创建无法登记的对象。

### T-12：重复 `initUpload` 的 URL 恢复

第一版采用短期缓存方案：

- [ ] UploadSession 临时保存 `upload_url` 和 `upload_headers`，TTL 不超过上传会话生命周期。
- [ ] `pending` 且 URL 未过期：返回原 Session 和 URL。
- [ ] `pending` 但 URL 已过期：返回明确过期结果，不能把旧 URL 当作可用。
- [ ] `ready`：返回幂等成功，不再生成新对象。
- [ ] `failed`：返回稳定失败原因；重新上传需要新的 `client_file_id`。
- [ ] 索引存在但 Session 不存在：记录脏数据并用带条件 Lua 安全清理。
- [ ] 后续再评估由 FileServer 为相同对象键刷新预签名 URL，不在第一版同时实现。

### T-13：幂等验收

- [ ] 同一用户、相同 `client_file_id` 顺序请求 10 次，只产生一个 Session 和一个对象键。
- [ ] 相同请求并发执行时，只允许一个请求调用 FileServer `InitUpload`。
- [ ] 相同 ID、相同元数据返回同一个上传任务。
- [ ] 相同 ID、不同大小或类型返回冲突。
- [ ] 不同用户使用相同 ID 不互相冲突。
- [ ] 同一用户的头像和聊天文件使用相同 ID 不互相冲突。
- [ ] FileServer 超时后，预约能够由持有者释放或自动过期。
- [ ] 幂等索引和 Session 的 TTL 不会产生永久脏 Key。

### T-14：头像并发完成顺序

- [ ] 设计“最后一次用户选择”标识，不能仅用“最后一次上传完成”判断最新头像。
- [ ] 可以在 Init 阶段记录 `latest_avatar_session_id` 或单调递增的头像意图版本。
- [ ] Complete 更新 MySQL 时使用条件更新，旧任务晚完成不能覆盖用户后来选择的新头像。
- [ ] 明确旧 Session Complete 时返回“已验证但不再生效”还是业务冲突。

## 11. R1：共享中间件与工程化重构（M1 验收后单独实施）

### 11.1 触发条件和边界

R1 只在头像后端闭环已经通过可重复端到端测试后开始，并使用独立提交完成。重构期间不同时增加好友、单聊、群聊或文件新功能，避免把业务缺陷和基础设施迁移问题混在一起。

- [ ] M1 的正常、重试和故障用例已有可重复验收记录，可作为重构回归基线。
- [ ] 重构只改变代码布局、依赖注入和构建关系，不改变 Redis Key、Lua 状态机、SQL 语义或对外消息协议。
- [ ] GateServer、ChatServer、StatusServer 等进程仍各自创建、拥有并关闭独立连接池；只共享实现代码，不共享跨进程运行时对象。
- [ ] 不为消除重复创建额外的集中式 `DataServer`，不在本阶段引入新的 RPC 跳转。
- [ ] 不在本阶段同时迁移 CMake、vcpkg/Conan、无锁队列或异步数据库驱动。

### 11.2 当前需要消除的重复

- [ ] 消除 GateServer 与 ChatServer 中重复的 `SqlConnection`、`MysqlPool`、`MysqlConnectionGuard` 和连接健康检查实现。
- [ ] 消除 GateServer、ChatServer、StatusServer 中重复的 `RedisReply`、`RedisPool`、`RedisConnectionGuard` 和连接健康检查实现。
- [ ] 将通用 Redis 命令执行与验证码、登录会话、上传会话等业务逻辑分开。
- [ ] 后续新增服务或 Repository 不得再复制现有 Pool、Guard 或 Reply RAII 代码。

### 11.3 建立共享基础设施静态库

目标布局：

```text
server/shared/
├── foundation/
│   ├── Result.h
│   └── Time.h
└── infrastructure/
    ├── mysql/
    │   ├── MysqlOptions.h
    │   ├── MysqlConnection.h
    │   ├── MysqlPool.h/.cpp
    │   ├── MysqlConnectionGuard.h
    │   └── MysqlTransaction.h/.cpp
    └── redis/
        ├── RedisOptions.h
        ├── RedisReply.h
        ├── RedisPool.h/.cpp
        ├── RedisConnectionGuard.h
        └── RedisClient.h/.cpp
```

- [ ] 在 `chat.sln` 新增静态库项目，例如 `ChatInfrastructure`，由需要中间件的服务通过 `ProjectReference` 链接。
- [ ] 共享库不得包含 GateServer 或 ChatServer 的 `ConfigMgr.h`、业务 `const.h`、JSON、Protobuf 和 Handler。
- [ ] `MysqlPool` 构造函数接收 `MysqlOptions`，由各服务读取自己的配置后注入。
- [ ] `RedisPool` 构造函数接收 `RedisOptions`，支持同一进程创建多个命名连接池，不能把单个全局 Singleton 作为长期唯一入口。
- [ ] 公共连接池统一处理借用超时、关闭、健康检查、归还和异常连接淘汰。
- [ ] 增加 RAII `MysqlTransaction`，保证异常路径执行回滚并恢复连接状态后再归还连接池。
- [ ] `RedisClient` 使用 hiredis argv 形式执行命令，不通过字符串拼接构造带用户数据的命令。

### 11.4 保留服务内业务 Repository

建议目标职责：

```text
GateServer
├── LoginRepository            MySQL 登录和注册数据
└── LoginSessionRepository     Redis Token、设备会话、验证码

ChatServer
├── UserProfileRepository      MySQL 用户资料
├── UploadSessionRepository    Redis 上传会话和 Lua 状态机
├── FriendRepository           MySQL 好友关系
└── MessageRepository          MySQL 消息持久化
```

- [ ] 将 `RedisFileMgr` 的长期职责明确为上传会话 Repository；可以暂时保留类名，但不能把 Lua 和上传状态机移入公共 RedisClient。
- [ ] 用户资料领域类型放入独立模型头文件，不依赖 MySQL、Redis 或网络协议。
- [ ] Handler 只调用 Manager/Application Service，不能直接接触 `sql::Connection`、`redisContext` 或连接 Guard。
- [ ] Repository/DAO 负责 SQL、Redis Key、Lua 和持久化结果；不构造 WebSocket JSON。
- [ ] Manager/Application Service 负责参数规则、调用顺序、幂等语义和错误映射；不负责连接借还。

### 11.5 多 Redis 和配置演进目标

- [ ] 第一版可以让登录 Session、上传 Session 和在线状态使用同一 Redis 实例，但 Key 必须使用独立命名空间。
- [ ] 构造方式必须允许未来通过配置拆为 `authRedis`、`uploadRedis`、`presenceRedis`，业务 Repository 不因拆实例而改接口。
- [ ] 密码、Token、SecretKey 等敏感配置不得输出到日志；长期迁移到环境变量或密钥管理，不硬编码在公共库。
- [ ] 绝对第三方依赖路径后续改由统一依赖管理或构建配置提供，但不与 R1 第一轮源码抽取同时进行。

### 11.6 R1 验收标准

- [ ] 仓库中只保留一份 MySQL Pool/Guard/Transaction 实现和一份 Redis Pool/Reply/Guard/Client 实现。
- [ ] GateServer 注册、登录和会话校验行为与重构前一致。

- [ ] 使用两组 Redis 配置构造两个 Pool 的小型测试通过，证明实现不再依赖唯一全局实例。
